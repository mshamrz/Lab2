# Нотатки для обговорення в класі

## Compose-файл

- **`image` vs `build`** — `image` тягне готовий образ (postgres:16); `build`
  збирає його з `Dockerfile` (backend, frontend). Бекенд і фронтенд наші —
  ми їх будуємо; Postgres — чужий, готовий.
- **`ports` vs `expose`** — `ports` публікує порт на хост-машину
  (`5432:5432` — доступ з ноутбука); `expose` лише відкриває порт іншим
  сервісам у тій самій compose-мережі, без виходу назовні. У нашому файлі
  все через `ports`, бо в деві зручно достукатись до бази напряму.
- **`environment`** — змінні середовища (`DATABASE_URL`, `CORS_ORIGINS`).
- **`volumes`** — `pgdata` зберігає дані Postgres між перезапусками;
  `./backend:/app` і `./frontend:/app` монтують код з хоста в контейнер,
  щоб зміни коду з'являлись без перезбирання образу.
- **`command`** — для frontend перевизначає команду запуску (`npm run dev`).
- **Що не годиться для продакшену:** монтування коду томом (`./backend:/app`)
  — у проді код має бути "запечений" в образ, а не підмінюватись з хоста;
  публікація порту Postgres на хост (5432) — у проді база не повинна бути
  доступна ззовні мережі взагалі.

## Готовність сервісів

`depends_on` без умови лише впорядковує **старт** контейнерів, не готовність
процесу всередині. Postgres-контейнер стартує за секунду, а сам сервер бази
даних приймає з'єднання на кілька секунд пізніше — бекенд встигне впасти,
намагаючись підключитись зарано.

Рішення: `healthcheck` на postgres (`pg_isready`) + `depends_on: condition:
service_healthy` на backend — тоді backend чекає, поки Postgres реально
відповідає, а не просто запустився.

Якщо база зникає **пізніше**, під час роботи (перезапуск, збій мережі),
жодна фіча compose не допоможе — це вже відповідальність коду: `pool_pre_ping`
у SQLAlchemy (є в нашому `database.py`) перевіряє з'єднання перед кожним
запитом і перепідключається; без цього застигле з'єднання видасть помилку,
поки процес не перезапустять вручну.

## Compose-файл vs Dockerfile

`Dockerfile` відповідає на питання «як зібрати один образ цього сервісу» —
базовий образ, залежності, команда запуску. `docker-compose.yml` відповідає
на питання «як кілька образів працюють разом на цій машині» — мережа,
порти, змінні середовища, порядок старту.

При переїзді на ECS/Cloud Run **Dockerfile лишається** — той самий образ
запускається і там. **Compose замінюється** на ECS task definition / Cloud
Run service config, бо оркестрація (скільки копій, як вони знаходять одна
одну, як масштабуються) там своя.

## Базовий образ

`python:3.12-slim` — Debian без зайвих утиліт і документації, менший за
повний `python:3.12`, але має `apt` для встановлення системних залежностей
(нам потрібен `libpq-dev` для psycopg2). Non-slim образ важчий і повільніше
збирається та деплоїться, але має більше готового «з коробки».

Alpine ще менший (використовує musl замість glibc), але: деякі Python-пакети
з C-розширеннями збираються довше або взагалі не мають готових wheel-ів під
musl, тож збірка стає повільнішою й крихкішою. Ми обрали `slim` як
компроміс: розумний розмір, стандартна glibc-сумісність.

## Backend

- **Структура:** HTTP-шар (`routers/meetings.py`) окремо від моделей даних
  (`models.py`) і від бізнес-логіки, яка поки що тривіальна й лежить прямо в
  роутері. Розділення важливе, коли логіка ускладниться: тоді HTTP-шар
  просто викликає окрему функцію/сервіс, а не змішує парсинг запиту,
  валідацію, запит до бази і формування відповіді в одному місці — це
  ускладнює і тестування, і читання.
- **SQLAlchemy:** мапить рядки таблиці на Python-об'єкти (`Meeting`).
  Виграш — не писати SQL руками для простих CRUD-операцій, типізація,
  міграції через Alembic знають про ту саму модель. Програш — у момент,
  коли запит стає складним (агрегації, віконні функції, специфічні для
  Postgres індекси), ORM або незручно виражає це, або генерує неоптимальний
  SQL, і доводиться писати сирий SQL через `text()`.
- **Alembic, а не `create_all()`:** `create_all()` створює таблиці, якщо їх
  ще немає, але не вміє **змінювати** існуючу таблицю, в якій уже є дані —
  додати колонку, перейменувати, змінити тип. Alembic — це версійована,
  ревʼюована й відкочувана зміна схеми. У нашому compose-файлі міграція
  запускається **при старті контейнера** (`CMD` у `backend/Dockerfile`:
  `alembic upgrade head && uvicorn ...`), не під час білда (тоді ще немає
  бази) і не вручну (це забудеться зробити).

## Деплой на AWS

- **Навіщо CloudFront, якщо S3 вже віддає файл по HTTP:** CloudFront додає
  HTTPS із сертифікатом, роздає файли з edge-локацій ближче до користувача
  (менша затримка), і дозволяє тримати бакет приватним — тільки CloudFront
  має право його читати.
- **ECR vs ECS:** ECR — реєстр образів (де лежить Docker-образ backend'а).
  ECS — оркестратор, який ці образи **запускає** як контейнери. Різні
  сервіси, бо зберігання образу і його виконання — різні відповідальності
  з різним масштабуванням.
- **Health check:** ALB регулярно стукає в `/health`; якщо контейнер
  перестає відповідати 200, ALB перестає слати йому трафік, а ECS вбиває
  такий таск і піднімає новий замість нього.
- **CNAME двічі:** перший раз — довести Route 53/ACM, що домен належить
  вам (запис, який просить опублікувати ACM); другий раз — направити
  реальний трафік (`api.domain` → ALB, `app.domain` → CloudFront). Перший
  — про підтвердження власності, другий — про маршрутизацію.
- **Витік access key vs OIDC-роль:** довготривалий ключ працює звідки
  завгодно і вічно, поки його не відкликати вручну. OIDC видає токен, що діє
  лише для одного запуску workflow, лише для вказаного репозиторію й гілки,
  і згасає разом із завершенням job. Якщо ключ витік — зловмисник має повний
  доступ, доки хтось не помітить. Якщо хтось скомпрометує CI-запуск з
  OIDC-роллю — вікно значно вужче і саме закривається.
- **Що виживе при 1000 організаціях, що зламається першим:** ALB, CloudFront
  і ECS переживуть масштабування без змін (просто більше тасків / інстансів
  за автоскейлінгом). Перше, що зламається — одна `db.t4g.micro` Postgres
  без реплік і без пулера з'єднань: вона впреться в CPU/IOPS і в ліміт
  одночасних з'єднань задовго до 1000 організацій.
