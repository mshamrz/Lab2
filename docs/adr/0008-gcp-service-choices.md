# ADR 0008: Вибір сервісів Google Cloud Platform (GCP) для міграції Spry

* **Статус:** Прийнято (Accepted)  
* **Дата:** 2026-11-09  
* **Автор:** Маріана Мороз (`m.moroz.pn@ucu.edu.ua`)  
* **Контекст:** Лабораторна робота 9 — Мультихмарна архітектура Spry (AWS vs GCP) та аналіз витрат

---

## 1. Контекст та проблема (Context)

У Лабораторних роботах 1–7 архітектура Spry була реалізована на базі Amazon Web Services (AWS) та описана в коді за допомогою Terraform:
- Статичний фронтенд у **S3** за дистрибуцією **CloudFront**;
- REST API на **FastAPI** в контейнерах **ECS Fargate / Lambda**;
- Реляційна база даних **PostgreSQL (RDS / Aurora Serverless v2)**;
- Аутентифікація через **AWS Cognito**;
- Асинхронні щотижневі звіти через **EventBridge Scheduler + SQS + SES**;
- AI-парсер адженди через **AWS Bedrock (Claude 3.5 Sonnet)**;
- Секрети та конфігурація в **AWS Secrets Manager / SSM Parameter Store**.

Перед архітектором постає стратегічне питання: **як перенести ядро системи на Google Cloud Platform (GCP), які сервіси вибрати для кожної підсистеми Spry, і скільки це коштуватиме порівняно з AWS?**

---

## 2. Порівняльна таблиця сервісів Spry (AWS vs GCP)

| Компонент Spry | Поточний сервіс на AWS | Сервіс на Google Cloud (GCP) | Рішення для Spry | Обґрунтування вибору |
|---|---|---|---|---|
| **Frontend + CDN** | S3 + CloudFront + WAF | **Firebase Hosting** | **Replace (Замінити)** | Firebase Hosting надає глобальний безкоштовний CDN, автоматичний SSL-сертифікат та підтримку rewrite-правил (`/api/**` на Cloud Run) без складного налаштування CloudFront Distributions та Load Balancers. |
| **Backend API** | ECS Fargate / Lambda + Function URL | **Cloud Run** | **Replace (Замінити)** | Cloud Run запускає стандартні Docker-контейнери, має автоматичний Scale-to-Zero (0 інстансів при відсутності запитів), вбудовану HTTPS-кінцеву точку та не вимагає адаптерів типу Mangum. Безкоштовний ліміт: 2 млн запитів/міс. |
| **Container Registry** | AWS ECR | **Artifact Registry** | **Replace (Замінити)** | Сучасний стандарт збереження Docker-образів у GCP (заміна старого Container Registry). 0.5 GB безкоштовно. |
| **Реляційна БД** | RDS / Aurora PostgreSQL | **Cloud SQL for PostgreSQL** (`db-f1-micro`) | **Replace (Замінити для ядра)** | Дозволяє зберегти 100% сумісність з існуючим кодом SQLAlchemy/Alembic без переписування схем та моделей. |
| **NoSQL БД (альтернатива)** | DynamoDB | **Cloud Firestore** | **Evaluate (Оцінено для оптимізації)** | Повністю безсерверна документна БД із безкоштовним рівнем (50 000 reads, 20 000 writes щодня), але вимагає повної відмови від SQL, Join та реляційних зв'язків. |
| **Аутентифікація** | AWS Cognito User Pool | **Identity Platform (Firebase Auth)** | **Keep on AWS (тимчасово)** | У рамках першого етапу міграції зберігаємо Cognito або використовуємо Google OAuth, оскільки перенесення користувачів є ризикованим для production-даних. |
| **Планувальник задач** | EventBridge Scheduler | **Cloud Scheduler** | **Replace (Замінити)** | Простий крон-сервіс із викликом HTTP-ендпоінтів Cloud Run. 3 безкоштовні задачі на платіжний акаунт. |
| **Черга повідомлень** | AWS SQS | **Cloud Pub/Sub** (або Cloud Tasks) | **Replace (Замінити)** | Cloud Tasks ближчий за семантикою до черги задач для виклику Cloud Run, тоді як Pub/Sub підходить для подієво-орієнтованої архітектури. |
| **Події сховища** | S3 Event Notifications | **Cloud Storage + Eventarc** | **Replace (Замінити)** | Eventarc перехоплює події Cloud Storage і безпечно маршрутизує їх у Cloud Run. |
| **Email-розсилка** | Amazon SES | **SendGrid / Mailgun** або **Keep AWS SES** | **Keep AWS SES (мультихмарно)** | У Google Cloud немає власного сервісу транзакційних листів (SMTP API). Найбільш прагматичний вибір — викликати Amazon SES з GCP або використати SendGrid. |
| **AI / LLM-парсер** | AWS Bedrock (Claude) | **Vertex AI (Gemini 1.5 Flash)** | **Replace (Замінити)** | Vertex AI надає доступ до Gemini 1.5 Flash (у 10–20 разів дешевше за Claude 3.5 Sonnet при відмінній якості вилучення структурованого JSON). |
| **Управління секретами**| AWS Secrets Manager | **GCP Secret Manager** | **Replace (Замінити)** | 6 активних версій секретів безкоштовно; нативна інтеграція з Cloud Run через автоматичне підмонтування у змінні середовища. |
| **Логування та моніторинг** | AWS CloudWatch Logs | **Cloud Logging & Monitoring** | **Replace (Замінити)** | 50 ГБ логів щомісяця безкоштовно; автоматичний збір `stdout/stderr` з Cloud Run без агента. |
| **IaC (Код інфраструктури)** | Terraform `aws` | **Terraform `google`** | **New (Окремий стан)** | Окрема директорія `gcp/` з незалежним terraform state, щоб помилки в одному хмарному провайдері не впливали на інший. |

## 3. Відповіді на ключові архітектурні питання

### 1. Вибір бази даних: Cloud SQL 24/7, Cloud SQL із зупинкою на ніч, Firestore чи збереження БД на AWS?

* **Варіант А: Cloud SQL for PostgreSQL 24/7 (`db-f1-micro`)**
  * *Вплив на затримку (Latency):* Мінімальна затримка (< 3–5 мс), оскільки Cloud Run і Cloud SQL розміщені в одному регіоні (`us-central1` або `europe-west3`) і з'єднані через внутрішній Cloud SQL Auth Proxy / Unix socket.
  * *Вплив на рахунок (Bill):* ~$7.67/міс за обчислення (730 год × $0.0105) + $1.70/міс за 10 GB SSD = **~$9.37/місяць**. На відміну від Aurora Serverless v2, Cloud SQL **не вміє ставати на паузу (auto-pause)** при простої.
  * *Вплив на код (Code):* **0 змін у коді**. Повна сумісність з існуючим `FastAPI + SQLAlchemy + asyncpg/psycopg2`.

* **Варіант Б: Cloud SQL із зупинкою на ніч (Cloud Scheduler)**
  * *Вплив на затримку:* Ідеальна в робочі години (8 годин/день), але **повна недоступність додатку вночі**, а холодний старт інстансу займає 2–3 хвилини.
  * *Вплив на рахунок:* Зменшує вартість обчислень до ~$2.50/міс (22 дні × 8 год = 176 год). Зберігання диску ($1.70) тарифікується постійно. Разом: **~$4.20/міс**.
  * *Вплив на код:* Не вимагає змін у коді додатку, але вимагає налаштування Cloud Scheduler + Cloud Functions/Workflows для включення/виключення.

* **Варіант В: Перехід на Google Cloud Firestore (NoSQL)**
  * *Вплив на затримку:* Відмінна (одиниці мілісекунд), горизонтальне масштабування з коробки.
  * *Вплив на рахунок:* **$0.00/місяць** для студентського та малого трафіку! Безкоштовний рівень скидається щодня: 50 000 читань, 20 000 записів і 1 ГБ сховища.
  * *Вплив на код:* **Колосальний перепис коду (High friction).** Немає реляційних зв'язків, немає зовнішніх ключів (Foreign Keys), відсутні `JOIN`. Потрібно повністю переписати схеми даних, перетворивши реляційні таблиці `meetings`, `agendas`, `attendees` на денормалізовані документи.

* **Варіант Г: Збереження БД на AWS та крос-хмарний доступ з GCP Cloud Run**
  * *Вплив на затримку:* **Катастрофічний (20–60 мс на кожен SQL-запит)** через мережевий овергед між дата-центрами AWS та GCP. Якщо один HTTP-запит робить 3–5 звернень до БД, затримка сторінки зростає на 150–300 мс.
  * *Вплив на рахунок:* Додаткові витрати на вихідний трафік AWS Internet Data Egress ($0.09 за кожний GB).
  * *Вплив на код:* Потребує налаштування публічного доступу до Aurora або коштовного VPN-тунелю Site-to-Site.

> **Архітектурне рішення:** Для забезпечення стабільності та працездатності Spry без переписування коду обираємо **Cloud SQL for PostgreSQL (`db-f1-micro`)** для ядра проекту, а для зменшення студентських витрат використовуємо скрипт зупинки інстансу після демонстрації. У звіті вартості також порівнюємо цей варіант із безкоштовним **Firestore**.

### 2. Електронна пошта (E-mail): який провайдер і де зберігається API-ключ?
Google Cloud Platform історично **не має власного SMTP/Transactional Email сервісу** (на відміну від Amazon SES).  
* **Обране рішення:** Використання **Amazon SES** або **SendGrid** (офіційний партнер GCP).
* **Безпека API-ключа:** Ключ доступу або SMTP-пароль ні в якому разі не комітяться в репозиторій. Він зберігається у **Google Cloud Secret Manager** як секрет `spry-email-api-key` і під час запуску монтується безпосередньо в середовище контейнера Cloud Run як змінна `EMAIL_API_KEY`.

### 3. Які сервіси Spry ми НЕ переносимо на GCP і чому?
1. **Користувацька база (AWS Cognito):**
   * *Чому не переносимо:* Міграція паролів користувачів між Cognito та Identity Platform неможлива безпосередньо (паролі хешовані різними солями). На першому етапі використовуємо федеративну аутентифікацію або валідуємо JWT-токени Cognito безпосередньо у FastAPI на Cloud Run.
2. **Щотижневий генератор звітів (Report Builder + Mailer на Lambda):**
   * *Чому не переносимо на першому етапі:* Він уже надійно працює за розкладом в AWS. Оскільки це фонова асинхронна задача, немає потреби витрачати зусилля на її переписування, якщо вона не впливає на основний користувацький інтерфейс.
3. **Bedrock AI інфраструктура:**
   * На AWS уже розгорнуто стек CloudFormation `spry-ai` з Function URL. На GCP ми створюємо альтернативний ендпоінт на базі **Vertex AI Gemini**, але зберігаємо зворотну сумісність.

## 4. Наслідки (Consequences)

### Позитивні:
- **Швидкість розгортання:** Cloud Run набагато зручніший для розробників за ECS/ALB: один контейнер отримує автоматичний HTTPS URL, авто-масштабування до 0 і не вимагає складних VPC та Target Groups.
- **Економічність API:** При відсутності трафіку Cloud Run коштує рівно $0.00.
- **Простота CDN:** Firebase Hosting автоматично проксує `/api/**` на Cloud Run, усуваючи будь-які проблеми з CORS між фронтендом і бекендом.
- **Ізоляція інфраструктури:** Нова конфігурація `gcp/` повністю ізольована від AWS Terraform, усуваючи ризик порушити роботу робочої версії на AWS.

### Негативні / Ризики:
- **База даних Cloud SQL не стає на паузу автоматично:** На відміну від Aurora Serverless v2, інстанс `db-f1-micro` продовжує тарифікуватися (~$9.37/міс), доки його явно не зупинити або видалити.
- **Відсутність рідного Email-сервісу:** Вимагає додаткової інтеграції зі сторонніми API (SendGrid) або мультихмарного зв'язку з AWS SES.
